партнёрских сервисов («Интеллектуальный домофон» и «Интеллектуальный

## 1. Что внедряем и почему это критично с т.з. безопасности

«Умный дом» в PropDevelopment — это интеграция, которая впервые в ландшафте:

1. **Делегирует управление физическим миром** (открытие двери, шлагбаума)
   внешней системе. Любая ошибка в авторизации = риск **физической безопасности**
   жильцов, а не только утечки данных.
2. **Обрабатывает биометрию** — это специальная категория ПДн по 152-ФЗ ст. 11
   с повышенными требованиями (отдельное согласие, СКЗИ).
3. **Подключает нового партнёра** к моб.приложению собственников — без сильной
   изоляции его влияние распространится далеко за рамки «Умного дома».

По матрице рисков из [Task 1](../Task1/README.md), данные «Умного дома»
(коды, биометрия) попадают в категорию **секретных**, риск утечки — **🔴
критический**, риск искажения — **🔴 критический**. Это рамки, в которых
формируем требования.

Из [Task 2](../Task2/README.md) сразу включаются контроли: **PARTNER-01..06**,
**PII-05**, **REG-06**, **API-04 (tenant-isolation)**, **SEC-04 (scope-bound
tokens)**, **AUDIT-01..02 (журналирование операций)**.

## 2. Новые и изменённые компоненты

### Новые контейнеры в PropDevelopment

- **`smart-home-bridge-app`** — единственная точка взаимодействия PropDev с
  партнёрской платформой. Прячет особенности партнёрского API, нормализует
  команды, кеширует ACL, валидирует webhook-события, применяет
  **tenant-isolation** (запрос разрешён, только если собственник владеет
  указанной квартирой).
- **`smart-home-db`** — локальная БД. Хранит:
  - правила доступа (кто-где-когда),
  - идемпотентные ключи операций,
  - **аудит-лог** всех событий открытия/отзыва.

  **Не хранит** биометрические шаблоны и raw-биометрию — они остаются на
  стороне партнёра, PropDev оперирует только идентификаторами шаблонов.

- **`webhook-receiver`** — публичный endpoint, на который Smart Home Platform
  присылает события «дверь открыта», «биометрия совпала», «команда выполнена».
  Логически — часть `smart-home-bridge-app`, выделено на схеме для ясности.

### Изменённые контейнеры

- **Моб.приложение собственников** — новые экраны: «Гости», «Машины»,
  «Биометрия», «Журнал доступа». Использует ровно тот же OIDC-flow, что
  и для прочих операций — отдельной авторизации для «Умного дома» нет,
  но появляются новые **scope** в выдаваемом JWT.
- **API Gateway / BFF** — если такого выделенного компонента ещё нет, он
  становится обязательным: он валидирует JWT, применяет rate-limit и
  маршрутизирует запросы. Это даёт единое место для применения политик
  безопасности к новым эндпоинтам.

### Новые внешние компоненты

- **Smart Home Platform** — партнёрская платформа. Состоит из (со стороны
  PropDev мы это знаем как чёрный ящик, но описываем для полноты): API
  для команд, контроллеров устройств, сервиса биометрии.
- **Видеодомофон** и **шлагбаум** — собственно железо в подъездах и на
  въездах. Управляются партнёром.

## 3. Принципы безопасной интеграции (общая стратегия)

Перед перечислением конкретных требований — пять принципов, из которых
эти требования вытекают.

1. **Single point of integration**. Только `smart-home-bridge-app` ходит во
   внешнюю платформу. Никакой компонент PropDev не должен звать партнёра
   напрямую — это позволяет применять единую политику в одном месте.
2. **Zero-trust между PropDev и партнёром**. Каждый запрос в обе стороны
   аутентифицирован (mTLS + bearer-token + HMAC для webhook). Ни одно
   действие не выполняется «по умолчанию», только по явному запросу.
3. **Data minimization** для ПДн и биометрии. PropDev передаёт партнёру
   ровно тот минимум, который нужен для матчинга (например, идентификатор
   квартиры, hash шаблона), и никогда — raw-биометрию или паспорт.
4. **Tenant-isolation** на каждом уровне. Жилой комплекс A не имеет
   возможности влиять на жилой комплекс B — ни через токен, ни через
   ошибку валидации, ни через API партнёра.
5. **Fail-safe для физических устройств**. Если внешняя платформа
   недоступна, домофон/шлагбаум **продолжают работать в классическом
   режиме** (звонок и/или ручное открытие), не блокируя жильцов в подъезде.

## 4. Требования к безопасности

Сгруппированы по 9 группам. Идентификаторы соответствуют разделам
проверочного листа из [Task 2](../Task2/README.md) для трассируемости.

### 4.1 Аутентификация (AUTH)

| ID | Требование |
| -- | ---------- |
| AUTH-T3-01 | Собственник аутентифицируется в моб.приложении по **OIDC + PKCE** через корпоративный IdP, без отдельной учётки для «Умного дома». |
| AUTH-T3-02 | `smart-home-bridge-app` обращается к Smart Home Platform по **OAuth 2.0 Client Credentials** (machine-to-machine), client_id и client_secret хранятся в Vault/K8s Secret. |
| AUTH-T3-03 | Канал между `smart-home-bridge-app` и Smart Home Platform обязательно использует **mTLS**: обе стороны валидируют сертификат партнёра, отзыв через CRL/OCSP. |
| AUTH-T3-04 | Webhook от Smart Home Platform проходит **тройную проверку**: mTLS на канале + HMAC-подпись тела + проверка `timestamp` в подписи (защита от replay). |
| AUTH-T3-05 | Срок жизни access-token — **≤ 15 минут**, refresh-token — **≤ 24 ч** с обязательной ротацией. JWT подписан **алгоритмом RS256+** (не HS256). |
| AUTH-T3-06 | Парные ключи и сертификаты ротируются **не реже 1 раза в год**; внеплановая ротация — при инциденте или уходе сотрудника партнёра, имевшего доступ. |

### 4.2 Авторизация (AUTHZ)

| ID | Требование |
| -- | ---------- |
| AUTHZ-T3-01 | JWT собственника содержит **scope**-claim вида `smarthome:door:open`, `smarthome:biometry:enroll`, `smarthome:vehicle:manage` и т.д. Эндпоинты `smart-home-bridge-app` проверяют наличие нужного scope. |
| AUTHZ-T3-02 | На каждый вызов `smart-home-bridge-app` проводит **tenant-check**: `owner_id` из токена должен владеть указанным `apartment_id`. Без этого запрос отклоняется (см. провал партнёрского API в [`lab/demo/02-cross-tenant.sh`](../lab/demo/02-cross-tenant.sh) — мы это не повторяем). |
| AUTHZ-T3-03 | Для добавления гостя/машины собственник обязан подтвердить операцию **2FA** (push-нотификация или TOTP). Это критическое действие, его нельзя выполнять автомолча. |
| AUTHZ-T3-04 | Менеджер УК имеет отдельные scope `smarthome:manager:*` и видит только тот ЖК, к которому привязан в AD. |
| AUTHZ-T3-05 | Партнёрский API имеет **scope, ограниченный одним жилым комплексом**: токен «УК Северный» не может ничего делать в данных «УК Южный» (контроль PARTNER-02 из Task 2). |

### 4.3 Защита API и контрактов (API)

| ID | Требование |
| -- | ---------- |
| API-T3-01 | Контракт `smart-home-bridge-app` ↔ Smart Home Platform формализован в **OpenAPI 3.1** с обязательным ревью специалистом ИБ перед каждым изменением. |
| API-T3-02 | В контракте **не передаются паспорт, ФИО полностью, дата рождения**. Партнёр получает: `tenant_id`, `apartment_id`, `owner_pseudonym` (UUID, не связанный с реальным id в PropDev), идентификатор биометрического шаблона. |
| API-T3-03 | Идемпотентные операции (включая выдачу гостевого доступа) защищены **idempotency key** в заголовке; ключи хранятся в `smart-home-db` ≥ 24 ч. |
| API-T3-04 | Rate-limit на webhook: ≤ 100 событий/сек на жилой комплекс; превышение → алерт в SIEM и временное приостановление обработки. |
| API-T3-05 | Внешние эндпоинты `webhook-receiver` доступны **только из IP-диапазонов партнёра** (allow-list) + WAF. |

### 4.4 Защита персональных данных (PII)

| ID | Требование |
| -- | ---------- |
| PII-T3-01 | Перед сбором биометрии собственник даёт **отдельное согласие** по форме, удовлетворяющей 152-ФЗ ст. 11; согласие хранится с цифровой подписью или фиксацией IP+timestamp. |
| PII-T3-02 | Биометрический шаблон **никогда не покидает Smart Home Platform** в сторону PropDev. PropDev хранит только идентификатор шаблона и метаданные (когда enroll, кем подтверждено). |
| PII-T3-03 | Право на удаление биометрии — реализовано как self-service в моб.приложении + автоматический вызов API партнёра. После удаления — подтверждающее событие через webhook и запись в аудит. |
| PII-T3-04 | Перед запуском в prod проведена **DPIA** (оценка влияния на ПДн) с регистрацией в журнале операторов ПДн. |
| PII-T3-05 | Локализация ПДн на территории РФ — закреплено DPA с партнёром (152-ФЗ ст. 18 ч. 5). |
| PII-T3-06 | В аудит-логи попадают **только идентификаторы** (`owner_pseudonym`, `apartment_id`, `event_id`); ФИО подгружаются на интерфейсе по запросу из `tenant-core-db`. |

### 4.5 Шифрование и каналы (CRYPTO)

| ID | Требование |
| -- | ---------- |
| CRYPTO-T3-01 | Все внешние каналы — **TLS 1.3** (TLS 1.2 разрешён только как fallback в первые 6 месяцев); внутренние каналы между `smart-home-bridge` и `tenant-core-db` — **mTLS внутри namespace** (Linkerd/Istio/cert-manager). |
| CRYPTO-T3-02 | `smart-home-db` шифруется **at-rest** (StorageClass с шифрованием + Postgres TDE для критичных колонок). |
| CRYPTO-T3-03 | Webhook-секреты (HMAC keys) хранятся в Vault, ротируются раз в 90 дней. |
| CRYPTO-T3-04 | Где есть требование 152-ФЗ к СКЗИ — используется криптонабор с ГОСТ-сертификатом (через ViPNet / КриптоПро); для прочих каналов — стандартный TLS с ECDHE+AES-GCM. |

### 4.6 Аудит и наблюдаемость (AUDIT)

| ID | Требование |
| -- | ---------- |
| AUDIT-T3-01 | Каждое событие доступа (запрос, решение, результат) пишется в `smart-home-db.audit_log` как **append-only** запись. |
| AUDIT-T3-02 | Лог реплицируется в DWH с ≤ 5 мин задержкой; в DWH данные хранятся **минимум 6 месяцев** (требование 152-ФЗ при инциденте) и **год для физических событий доступа**. |
| AUDIT-T3-03 | Алерты в SIEM на: ≥10 неуспешных биометрических матчей за минуту для одного собственника; открытие двери ночью у собственника без графика; падение mTLS-соединения с платформой. |
| AUDIT-T3-04 | Самообслуживание собственника (добавил/удалил гостя, отозвал биометрию) логируется отдельно с уведомлением **по альтернативному каналу** (email или SMS) — для раннего обнаружения компрометации аккаунта. |

### 4.7 Сеть и сегментация (NET)

| ID | Требование |
| -- | ---------- |
| NET-T3-01 | `smart-home-bridge-app` работает в выделенном **namespace `smart-home`** с NetworkPolicy: ingress только от API Gateway, egress — только в `tenant-core-db` (read-only сервис-аккаунт), `smart-home-db` и наружный IP партнёра. |
| NET-T3-02 | `webhook-receiver` выставляется на отдельный hostname с WAF; не делит pod с другими компонентами. |
| NET-T3-03 | Egress в Smart Home Platform идёт через корпоративный исходящий proxy с фиксированным внешним IP — это упрощает партнёру allow-list на их стороне. |

### 4.8 Управление секретами (SEC)

| ID | Требование |
| -- | ---------- |
| SEC-T3-01 | client_id/client_secret, mTLS-сертификаты, HMAC-секреты webhook'а — в Vault; в манифесты K8s попадают только через **ExternalSecrets** оператор. |
| SEC-T3-02 | Никаких секретов в Git, build-логах, отладочных дампах. CI настраивает scan на secret-leak. |
| SEC-T3-03 | Сертификаты mTLS выпускаются **закрытым внутренним CA** с временем жизни ≤ 90 дней, ротация — cert-manager. |

### 4.9 Резильентность и устойчивость (RES)

| ID | Требование |
| -- | ---------- |
| RES-T3-01 | Smart Home Platform недоступна → домофон работает по звонку (классический режим). Эта логика реализована на стороне устройства/партнёра и закреплена SLA. |
| RES-T3-02 | `smart-home-bridge-app` имеет **circuit breaker** на исходящие вызовы (5-15 с тайм-аут, открывается при ≥50% ошибок за окно 30 с). |
| RES-T3-03 | Очередь обработки webhook-событий с DLQ; повторная обработка через экспоненциальный backoff. |
| RES-T3-04 | SLA партнёра по доступности — **≥99.5%** на API и **≥99.9%** на работу физических устройств в офлайн-режиме. |

### 4.10 Соответствие регулятору (REG)

| ID | Требование |
| -- | ---------- |
| REG-T3-01 | Подписан **DPA с партнёром** (data processing agreement) с явным перечислением передаваемых полей. |
| REG-T3-02 | Партнёр включён в реестр операторов ПДн PropDev (или подтверждён собственный статус). |
| REG-T3-03 | Биометрия → отдельное согласие, отдельный реестр. |
| REG-T3-04 | Уведомление РКН об инциденте с ПДн — в течение 24 часов (152-ФЗ ст. 21). |

## 5. Протоколы аутентификации и авторизации (свод)

### Резюме по каналам

| Канал | Кто кого аутентифицирует | Протокол | Защита целостности |
| ----- | ------------------------ | -------- | ------------------ |
| Собственник → моб.приложение | Корп. IdP | OIDC + PKCE | TLS 1.3 |
| Моб.приложение → API Gateway | IdP-signed JWT (RS256) | OAuth 2.0 Bearer | TLS 1.3 |
| API Gateway → внутренние сервисы | Внутренний CA, service-account JWT | mTLS внутри namespace | mTLS |
| `smart-home-bridge` → Smart Home Platform | Внешний клиент-сертификат + bearer | OAuth 2.0 Client Credentials | mTLS + JWT |
| Smart Home Platform → `webhook-receiver` | Внешний клиент-сертификат | mTLS + HMAC-SHA256 на body | mTLS + HMAC + timestamp |
| Менеджер УК → админ-UI | Корп. IdP с MFA | OIDC + второй фактор | TLS 1.3 |

### Зачем именно так

- **OIDC + PKCE для моб.приложения** — стандарт OAuth 2.1, защищает от
  перехвата authorization code на мобильных устройствах. Не используется
  client_secret в коде приложения (его всё равно нельзя там безопасно
  хранить).
- **OAuth 2.0 Client Credentials для M2M** — соответствует сценарию: машина
  машине, без участия пользователя. PKCE и user-flows здесь не применимы.
- **mTLS поверх OAuth** — двойная защита: даже если кто-то получил
  bearer-token, без правильного клиентского сертификата он не дозвонится
  до партнёрского API. Это **существенно** уменьшает blast radius утечки
  токена.
- **HMAC на webhook** — единственный способ удостовериться, что событие
  пришло именно от партнёра, а не подделано. Дополнительный `timestamp` в
  подписи защищает от replay.

## 6. Описание взаимодействия — основные потоки

Чтобы требования стали наглядными, ниже основные use case-ы с указанием,
какие компоненты задействованы и где применяется какой контроль.

### 6.1 Onboarding собственника с биометрией

```
Собственник → Моб.приложение → API Gateway → smart-home-bridge-app
                                               │
            (1) Проверка scope smarthome:biometry:enroll
            (2) Проверка tenant: owner владеет квартирой
            (3) Запись согласия в smart-home-db.consents
                                               │
                                               ↓
                          Smart Home Platform (enroll биометрии)
                                               │ возвращает template_id
                                               ↓
            (4) Сохранение template_id и метаданных в smart-home-db
            (5) Запись в audit_log: «enrolled»
            (6) Push-уведомление собственнику об успехе
```

Контроли, которые проявляются:
- `AUTHZ-T3-01`, `AUTHZ-T3-02` (scope + tenant-check)
- `PII-T3-01`, `PII-T3-02` (согласие + биометрия не уходит к PropDev)
- `AUDIT-T3-01`, `AUDIT-T3-04` (аудит + альтернативный канал уведомления)

### 6.2 Открытие двери по биометрии (event flow)

```
Гость → Видеодомофон (распознавание лица)
            │
            ↓ команда «open?»
       Smart Home Platform
            │ матч → решение «open»
            ↓ webhook
       webhook-receiver
            │ (1) mTLS termination на ingress
            │ (2) HMAC-проверка + timestamp
            │ (3) Идемпотентный ключ по event_id
            ↓
       smart-home-bridge-app
            │ запись в smart-home-db.audit_log
            ↓
       Push в моб.приложение собственника
       (информативный — он узнал, что в его дом вошли)
```

Контроли:
- `AUTH-T3-04` (тройная защита webhook)
- `API-T3-03` (идемпотентность)
- `AUDIT-T3-01`, `AUDIT-T3-02` (запись в локальный лог и реплика в DWH)

### 6.3 Отзыв доступа гостя

```
Собственник → Моб.приложение → 2FA-подтверждение
                              ↓
                       API Gateway → smart-home-bridge-app
                              │ (1) scope smarthome:guest:manage
                              │ (2) tenant-check
                              ↓
                       Smart Home Platform: revoke access
                              ↓ ack
                              ↓ webhook «revoked»
                       smart-home-bridge-app
                              │ запись в audit_log
                              ↓
                       Push владельцу + email (альт.канал)
```

Контроли:
- `AUTHZ-T3-03` (2FA для критических операций)
- `AUDIT-T3-04` (альт.канал уведомления — защита от компрометации мобильного клиента)

### 6.4 Партнёр УК настраивает правила доступа

```
Менеджер УК → Админ-UI → API Gateway → tenant-core-app
                                          ↓
                                   smart-home-bridge-app
                                          │ tenant-check: УК = текущий ЖК
                                          ↓
                                   Smart Home Platform
```

Контроли:
- `AUTHZ-T3-04`, `AUTHZ-T3-05` (изоляция между УК; см. провал в `lab/demo/02-cross-tenant.sh`)

### 6.5 Сценарий отказа Smart Home Platform

```
Smart Home Platform недоступна
            │
            ↓
   smart-home-bridge-app фиксирует ошибку, открывает circuit breaker
            │
            ↓
   API Gateway возвращает в моб.приложение «временно недоступно»
            │
            ↓ ПАРАЛЛЕЛЬНО
   Домофон переходит в офлайн-режим: только звонок жильцу
   Шлагбаум: только ручное открытие (брелок / пульт охраны)
```

Контроли:
- `RES-T3-01`, `RES-T3-02` (fail-safe + circuit breaker)
- Бизнес-инвариант: жильцы в любом случае могут попасть домой
