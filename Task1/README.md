# Task 1. Проверочный лист по безопасности данных PropDevelopment

Документ — текстовый источник для mindmap. Mindmap в `Task1/mindmap.drawio`
визуализирует те же данные.

## Методика

- **Стандарты**: ISO/IEC 27001:2022 (control A.5.12 — *Classification of information*)
  и ISO/IEC 27002:2022 (control 5.12 + guidance 5.13 — *Labelling*).
  Классификация выполнена по принципу «требуемого уровня защиты» исходя из
  ущерба при компрометации.
- **4 категории данных** (из задания): публичные / внутренние / конфиденциальные / секретные.
- **5 рисков** (из задания): утечка / потеря / искажение / некачественные данные / обесценивание.
- **Шкала оценки** (из задания): незначительный / значительный / критический.
  В тексте сокращаем как 🟢 / 🟡 / 🔴.
- **Юрисдикция**: явно зафиксировано «требования законодательства
  РФ», то есть PropDevelopment рассматривается как российская компания.
  Поэтому далее ссылки на конкретные законы — это акты РФ (152-ФЗ о ПДн,
  214-ФЗ о долевом строительстве, статьи УК РФ). Для другой юрисдикции — например,
  Казахстан — это были бы аналоги: Закон РК «О персональных данных и их защите»
  № 94-V, Закон РК «О долевом участии в жилищном строительстве» № 486-V,
  ст. 253 УК РК и т.д.

Для каждого типа данных указан один-два наиболее актуальных риска (а не все
пять), потому что в реальности именно эти риски формируют профиль угроз
конкретного типа. На mindmap отражены те же связи.

## 1. Классификация типов данных

### 1.1 Публичные данные

Доступны любому лицу без ограничений. Утечка не приносит ущерба, потому что
данные изначально предназначены к публикации.

| Тип данных                                   | Где живут в ландшафте                       |
| -------------------------------------------- | -------------------------------------------- |
| Каталог недвижимости (адреса, планировки, цены) | Витрина продаж (`client-mart-app` + БД)      |
| Маркетинговые материалы и рекламные тексты   | Витрина продаж, сайт                          |
| Контактные данные офисов и компании          | Витрина продаж, корпоративный сайт            |
| Обязательная отчётность застройщика          | Отдельный публичный канал (закон 214-ФЗ)      |

### 1.2 Внутренние данные

Предназначены для сотрудников и систем PropDevelopment. Утечка ведёт к
ограниченному репутационному или операционному ущербу, но не задевает
напрямую клиентов и не подпадает под 152-ФЗ.

| Тип данных                                   | Где живут в ландшафте                       |
| -------------------------------------------- | -------------------------------------------- |
| Архитектурная и техническая документация      | Внутренние wiki, репозитории                  |
| Логи приложений без ПДн                      | Все сервисы → хранилище данных (`DWH`)        |
| Агрегированная аналитика и BI-метрики         | Домен «Дата» (BI, отчётность)                 |
| Графики строительства и планы ремонта         | `tenant-core-app`, внутренние системы УК      |

### 1.3 Конфиденциальные данные

Сюда попадает большинство ПДн и бизнес-данных, регулируемых 152-ФЗ. Утечка
ведёт к ответственности перед регулятором, потере доверия клиентов и
финансовым потерям. Это центр внимания аудита безопасности.

| Тип данных                                   | Где живут в ландшафте                       |
| -------------------------------------------- | -------------------------------------------- |
| ПДн клиентов: ФИО, телефон, email, расширенная форма | `client-mart-app`, `client-crm-app`     |
| ПДн собственников                            | `tenant-core-app`, `crm-tenant`               |
| Данные бронирований и записи онлайн-туров    | `client-mart-app`, `client-tour-app`          |
| Контракты онлайн-сделок                      | `client-mart-app`, интеграции с госорганами   |
| Платёжные операции и обращения в УК ЖКУ       | `tenant-core-app`, биллинг                    |

### 1.4 Секретные данные

Высший уровень защиты. Компрометация → катастрофические последствия:
финансовые потери, нарушение закона, угроза физической безопасности
жильцов (через «Умный дом»). По ISO 27002 такие данные требуют
криптографической защиты, отдельных каналов доставки и журналирования
любого доступа.

| Тип данных                                   | Где живут в ландшафте                       |
| -------------------------------------------- | -------------------------------------------- |
| Паспортные и финансовые данные физлиц (сделка) | `client-mart-app`, интеграция с банками/госорганами |
| Учётные записи и пароли (Active Directory)   | AD-сервисы (есть в двух доменах)              |
| API-токены партнёров и криптоключи           | Все интеграции, особенно `partner-api` УК     |
| Финансовая отчётность компании до публикации | `accountant-service-1`                        |
| Данные доступа к «Умному дому» (коды, биометрия) | `tenant-core-app` + будущие сервисы Task 3 |

## 3. Обоснование оценок (то, что попадёт в листья mindmap)

Ниже — главные риски по каждому типу с пояснениями. На mindmap эти строки
становятся последним уровнем («Почему именно такая оценка»).

### 3.1 Публичные

- **Каталог недвижимости — Потеря: 🟡.** При недоступности базы каталога витрина
  продаж не функционирует, лиды не поступают. Не катастрофа (есть резервные
  копии), но прямой удар по выручке.
- **Каталог недвижимости — Искажение: 🟡.** Подмена цены или планировки уронит
  доверие к застройщику и спровоцирует юридические претензии (нарушение
  публичной оферты).
- **Маркетинговые материалы — Искажение: 🟡.** Defacement сайта = удар по
  бренду, но обратимый.
- **Контактные данные офисов — Искажение: 🟡.** Подмена номера телефона
  включает классический фишинг под «горячую линию».
- **Обязательная отчётность — Искажение: 🔴.** Отчёт по 214-ФЗ — публичный
  документ с юридической силой. Искажение = уголовная ответственность.

### 3.2 Внутренние

- **Архитектурная документация — Утечка: 🟡.** Знание архитектуры упрощает
  атаки и облегчает работу конкурентам, но прямого ущерба ПДн нет.
- **Логи приложений — Искажение: 🔴.** Если злоумышленник может менять логи,
  любой инцидент становится невосстановимым. Это атакующий слой контроля
  безопасности (см. Task 6 — аудит).
- **Аналитика и BI-метрики — Некачественные: 🔴.** Прямо названная в кейсе
  цель: «компания планирует ML/AI-сервисы». Грязные данные → невалидные
  модели → ошибочные продуктовые решения.
- **Графики строительства — Искажение: 🟡.** Подмена графика → срыв сроков,
  но обратимо при бэкапах.

### 3.3 Конфиденциальные

- **ПДн клиентов — Утечка: 🔴.** Это и есть инцидент у конкурента из кейса.
  152-ФЗ, штрафы до 18 млн ₽ за крупную утечку, репутация, отзывы.
- **ПДн клиентов — Потеря: 🔴.** Без них невозможно завершить сделки и
  выполнить обязательства по 214-ФЗ.
- **ПДн клиентов — Искажение: 🔴.** Изменение ФИО/паспорта в сделке = повод
  для оспаривания договора, юридическая катастрофа.
- **ПДн клиентов — Некачественные: 🟡.** Прямо моделируется в нашей лабе
  (`./demo/04-duplicate-clients.sh`): mart и crm имеют конфликтующие записи
  одного клиента → жалоба «в ЛК виден чужой ФИО» из кейса.
- **ПДн собственников — те же риски, что и у клиентов.** Дополнительно —
  «Умный дом» добавит зависимость физической безопасности от целостности
  привязки «собственник → квартира».
- **Бронирования и онлайн-туры — Искажение: 🔴.** Запись осмотра — юридический
  факт; подмена результата осмотра меняет условия сделки.
- **Контракты онлайн-сделок — Утечка: 🔴.** Включают паспорт, сумму, реквизиты
  — все одновременно. Идеальный набор для мошенничества.
- **Контракты — Потеря: 🔴.** Обязаны храниться 5+ лет по 214-ФЗ и НК РФ.
- **Платёжные операции ЖКУ — Утечка: 🔴.** Содержат банковские реквизиты,
  суммы платежей, привязку к адресу. Подходит для социальной инженерии.
- **Платёжные операции ЖКУ — Искажение: 🔴.** Подмена назначения платежа =
  прямое финансовое мошенничество.

### 3.4 Секретные

- **Паспортные и финансовые данные — Утечка: 🔴.** Один из самых ценных
  наборов на чёрном рынке: позволяет оформить кредит на чужое имя.
- **Учётные записи / AD — Утечка: 🔴.** Скомпрометированный AD = полная
  компрометация всех систем, потому что AD = единая точка аутентификации.
- **Учётные записи / AD — Потеря: 🔴.** Потеря AD = офис не работает,
  никто не входит в системы.
- **API-токены партнёров — Утечка: 🔴.** Прямо упомянуто в кейсе: «контракты
  позволяют партнёру одной УК видеть данные другой». В лабе моделируется
  как `./demo/02-cross-tenant.sh`. Утечка токена расширяет проблему до
  «партнёр видит всех».
- **API-токены — Искажение: 🔴.** Подмена токена в конфиге = atomic-перехват
  интеграции.
- **Финансовая отчётность до публикации — Утечка: 🔴.** Инсайдерская
  информация, ст. 185.6 УК РФ. Также — конкурентное преимущество.
- **Данные «Умного дома» — Утечка: 🔴.** Коды квартир в чужих руках =
  физический доступ к жилью. Это уже не финансовый, а буквально
  «безопасность жизни». Биометрия по 152-ФЗ относится к специальным
  категориям ПДн с повышенными требованиями.
- **Данные «Умного дома» — Искажение: 🔴.** Подмена кода замка или белого
  списка лиц для домофона = аналогичные риски.

## 4. Что отсюда вытекает для следующих заданий

Из проверочного листа уже видна логика следующих заданий спринта:

- **Конфиденциальные ПДн** распылены по `mart-app` и `crm-app` без единого
  контракта данных → отсюда требование к проверочному листу бизнес-систем
  в **Task 2**.
- **Секретные API-токены партнёров и данные «Умного дома»** → формируют
  требования к безопасной интеграции в **Task 3** (новые партнёрские
  сервисы домофона и шлагбаума).
- **Доступ к секретным данным внутри кластера** должен быть ограничен по
  ролям и сетям → **Task 4 (RBAC), Task 5 (NetworkPolicy), Task 7 (PSA/OPA)**.
- **Целостность внутренних логов** (риск «искажение: 🔴») напрямую
  диктует требования к аудиту в **Task 6**.
