# Task 2. Проверочный лист безопасности для бизнес-систем PropDevelopment

Проверочный лист — это инструмент аудита, который структурирует требования
безопасности по разделам и привязывает их к конкретным системам. Этот
документ — основа для предстоящего комплексного аудита PropDevelopment.

## Методика

- **Источники**: ISO/IEC 27002:2022 (Annex A controls), OWASP ASVS v4.0
  (раздел V1–V14), NIST CSF v2.0 (Identify/Protect/Detect/Respond/Recover),
  152-ФЗ и 214-ФЗ (юрисдикция РФ зафиксирована в `zadanie.txt`).
- **Подход**: не плоский «всё подряд», а отбор разделов, которые покрывают
  проблемы кейса и категории данных, выделенные в [Task1](../Task1/README.md).
- **Связь с Task 1**: каждый раздел листа явно указывает, какие категории
  данных (публичные / внутренние / конфиденциальные / секретные) он защищает.
- **Связь с лабой**: в колонке «Обнаружения» где возможно даю ссылку на
  конкретный воспроизводимый сценарий из `lab/demo/` — это превращает чек-лист
  из теоретического в доказательный.

## Шкала статусов

| Статус | Значение |
| :----: | -------- |
| ✅     | Контроль реализован и подтверждён |
| ⚠️     | Контроль частично реализован или есть пробелы |
| ❌     | Контроль не реализован, проблема подтверждена |
| ❓     | Недостаточно данных в кейсе, нужен аудит на месте |

## Шкала приоритетов

| Приоритет | Когда применяется |
| --------- | ----------------- |
| 🔴 **Высокий** | Затронуты конфиденциальные/секретные данные или явная проблема кейса |
| 🟡 **Средний** | Внутренние данные или операционные риски |
| 🟢 **Низкий**  | Публичные данные или соответствие best-practice без критических последствий |

## 1. Идентификация бизнес-систем PropDevelopment

Систематизация ландшафта из C4-диаграммы по доменам. Для каждой системы
определены: характер данных, уровень доступа и регуляторная нагрузка.

| Система | Домен | Данные (по Task 1) | Внешний доступ | Регулятор |
| ------- | ----- | ------------------ | :------------: | :-------: |
| **Витрина продаж** | Продажи | Публичные + контактные ПДн | ✅ HTTPS | 152-ФЗ |
| `client-mart-app` + `client-mart-db` | Продажи | Конфиденциальные (ПДн, бронирования) + секретные (паспорт, фин.данные сделки) | ✅ через витрину | 152-ФЗ, 214-ФЗ |
| `client-mart-estate-app` + `client-mart-estate-db` | Продажи | Публичные (каталог объектов) + внутренние (планы) | ✅ через витрину | — |
| `client-tour-app` | Продажи | Конфиденциальные (записи онлайн-туров с лицами) | ✅ через витрину | 152-ФЗ |
| `client-crm-app` + `crm-db` | Продажи | Конфиденциальные (ПДн клиентов, история взаимодействий) | ❌ только внутр. | 152-ФЗ |
| `auth-service-1` + `auth-db-1` | Продажи | Секретные (учётные данные клиентов) | Через витрину | 152-ФЗ |
| **Витрина сервисов для собственников** | ЖКУ | Публичные + контактные | ✅ HTTPS | 152-ФЗ |
| `tenant-core-app` + `tenant-core-db` | ЖКУ | Конфиденциальные (ПДн собственников, платежи, ремонт) + секретные (коды «Умного дома», биометрия) | ✅ через витрину | 152-ФЗ |
| CRM собственников + `crm-tenant-db` | ЖКУ | Конфиденциальные (ПДн) | ❌ только внутр. | 152-ФЗ |
| `accountant-service-1` + `acc-db-1` | Финансы | Секретные (фин.отчётность до публикации) | ❌ только внутр. | НК РФ, инсайдерское регулирование |
| **Active Directory** (2 экземпляра) | Продажи + Финансы | Секретные (учётные данные сотрудников) | ❌ только внутр. | 152-ФЗ (ПДн сотрудников) |
| **Хранилище данных (DWH)** | Дата | Внутренние + конфиденциальные (агрегированные ПДн) | ❌ только внутр. | 152-ФЗ |
| **BI и отчётность** | Дата | Внутренние | ❌ только внутр. | — |
| **Партнёрские системы УК** | ЖКУ (внешние) | Конфиденциальные (ПДн собственников) + секретные (API-токены) | ✅ через API | 152-ФЗ |
| **Госорганы (Росреестр и др.)** | Продажи (внешние) | Секретные (паспорта, кадастр) | ✅ через API | 152-ФЗ, 214-ФЗ |
| **Платёжные системы** | ЖКУ + Продажи (внешние) | Секретные (платёжные данные) | ✅ через API | ФЗ-161 о НПС |

**Итого**: ~16 идентифицируемых систем; 6 имеют внешний доступ; 10 хранят
конфиденциальные или секретные данные → большая часть ландшафта работает
под регуляторной нагрузкой.

## 2. Выбор разделов проверочного листа

Полный список тематических разделов из ISO 27002 содержит десятки контролей.
Включаем только те разделы, где у PropDevelopment есть либо подтверждённая
проблема из кейса, либо высокий риск по Task 1.

| Раздел | Почему включаем | Связь с кейсом | Связь с Task 1 |
| ------ | --------------- | -------------- | -------------- |
| **AUTH** — Аутентификация | Не отделена от авторизации; «токены» в `client-mart-app` тривиальны | IDOR в ЛК клиента | Конфиденциальные, секретные |
| **AUTHZ** — Авторизация и контроль доступа | Прямая причина утечки в ЛК | «В ЛК виден чужой ФИО» | Все категории с ограниченным доступом |
| **API** — Контракты и безопасность API | Партнёрские API без единой политики | «контракты позволяют партнёру одной УК видеть данные другой» | Конфиденциальные + секретные |
| **PII** — Обработка персональных данных | Цель аудита явно по 152-ФЗ | Жалобы клиентов, инцидент у конкурента | Конфиденциальные, секретные |
| **AUDIT** — Журналирование и аудит | Без целостного аудита нельзя расследовать инциденты | «отреагировать на инциденты и рыночные изменения» | Все, но критично для конф./секр. |
| **CRYPTO** — Шифрование | Нет упоминания о шифровании ПДн и токенов; high-impact пробел | По умолчанию пробел; явно требует 152-ФЗ ст. 19 | Конфиденциальные, секретные |
| **NET** — Сетевая сегментация | Внутри K8s «open relay» (лаба `demo/05`) | «нет системного контроля» | Все |
| **SEC** — Управление секретами | API-токены УК и AD-учётки — наиболее ценная цель атак | Партнёрские API, секретность кодов «Умного дома» | Секретные |
| **K8S** — Безопасность платформы | Прямой предмет Task 4–7 спринта | RBAC, NetworkPolicy, PSA, аудит — всё в задании | Все |
| **BACKUP** — Резервное копирование | Кейс упоминает резервное копирование, но без оценки полноты | «выполняется резервное копирование на нужную глубину» | Конфиденциальные, секретные |
| **VULN** — Управление уязвимостями и патчинг | Стандартная компонента ISO 27002, без неё аудит неполный | По умолчанию пробел | Все |
| **IR** — Реагирование на инциденты | Прямой триггер — инцидент у конкурента | «отреагировать на инциденты» | Все |
| **PARTNER** — Безопасность партнёрских интеграций | Отдельный раздел из-за остроты проблемы | Прямо одна из двух глобальных проблем | Конфиденциальные + секретные |
| **REG** — Соответствие законодательству РФ | Прямая бизнес-цель аудита | «требования законодательства РФ» | Конфиденциальные, секретные |

**Что осознанно НЕ включили** и почему:
- *Безопасность мобильных устройств сотрудников (BYOD/MDM)* — кейс не упоминает удалённую работу как фактор риска.
- *Физическая безопасность ЦОД* — есть свой ЦОД, но в задании нет указания на физические инциденты.
- *Безопасность жизненного цикла ПО (SDLC, SAST/DAST)* — важно, но не на первой итерации; задели частично через VULN.
- *Security awareness тренинги* — кейс упомянул «специалист по ИБ один на компанию», но это организационная проблема. Косвенно покрыто в IR (готовность к инцидентам).

## 3. Проверочный лист

Сокращения колонок: **ID** — идентификатор контроля; **Системы** — где
применяется (или [Все]); **Прио** — приоритет; **Обнаружения** —
выявленные факты из кейса/лабы (если есть).

### 3.1 AUTH — Аутентификация

| ID | Контроль | Системы | Статус | Обнаружения | Прио |
| --- | -------- | ------- | :----: | ----------- | :--: |
| AUTH-01 | Единая система аутентификации (SSO) для клиентских приложений | `client-mart-app`, `client-tour-app`, витрина продаж | ❓ | На C4 есть `auth-service-1` для домена Продаж, но непонятно, охватывает ли все приложения | 🟡 |
| AUTH-02 | Использование стойких паролей (длина ≥12, сложность) и MFA для админских ролей | AD ×2, `accountant-service-1` | ❓ | Кейс не описывает парольную политику | 🔴 |
| AUTH-03 | Срок жизни токена ограничен и явно валидируется на сервере | Все API | ❌ | В `lab/services/client-mart-app/app/main.py` «токен» = `mart-<user_id>`, без подписи и срока. Воспроизводится в `lab/demo/01` | 🔴 |
| AUTH-04 | Защита от перебора (rate limiting, lockout) на эндпоинтах входа | Витрины продаж и ЖКУ, моб.приложение | ❓ | Не упомянуто | 🟡 |
| AUTH-05 | Хранение паролей в виде криптостойких хэшей (bcrypt/argon2) | `auth-db-1`, AD | ❓ | Не упомянуто. В лабе хранятся в плейн-тексте — пометка для аудита | 🔴 |
