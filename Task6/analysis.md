# Отчёт по результатам анализа Kubernetes Audit Log

## Исходные данные

- Период наблюдения: запуск `simulate-incident.sh` (см. файл в этой же папке).
- Источник: `/var/log/kubernetes-audit.log` внутри ноды Minikube,
  выгружен в `audit.log` (≈2600 строк), отфильтровано в
  `audit-extract.json` (7 подозрительных событий).
- Кластер: Minikube v1.38.1 с включённой `audit-policy.yaml` (level
  RequestResponse для pods/secrets/configmaps/serviceaccounts/RBAC,
  level Metadata — для остального).

## Подозрительные события

### 1. Доступ к секретам (`secrets-access`)

- **Кто**: `user=minikube-user` (cluster-admin), который **подменяет**
  свою идентичность через `--as=system:serviceaccount:secure-ops:monitoring`.
- **Где**: `LIST secrets` в `kube-system`.
- **Результат**: `403 Forbidden` — встроенный RBAC заблокировал.
  ServiceAccount `monitoring` не имеет права читать секреты в
  `kube-system`.
- **Почему подозрительно**: попытка узнать содержимое секретов из
  привилегированного `kube-system` от имени «мониторингового» аккаунта —
  типичный шаблон lateral movement. Не важно, что отказ; сам факт
  попытки + использование impersonation = ранний индикатор атаки.
- **Какой контроль провален** (см. [Task 2](../Task2/README.md)):
  `AUDIT-01` — событие зафиксировано **только потому**, что включён
  Audit. До настройки этой задачи такие пробы остались бы невидимыми.

### 2. Создание привилегированного пода (`privileged-pod`)

- **Кто**: `minikube-user` (cluster-admin).
- **Где**: namespace `secure-ops`, под `privileged-pod` с
  `securityContext.privileged: true`.
- **Результат**: `201 Created` — апи-сервер принял манифест.
- **Почему подозрительно**: privileged-pod получает доступ к host-уровню,
  откуда можно вырваться в ноду (CVE-эксплойты, mount /, доступ к
  kubelet credentials). На прод-кластере такой запрос должен блокироваться
  PodSecurity Admission или OPA Gatekeeper.
- **Какой контроль провален**: `K8S-03` и `K8S-07` из Task 2 —
  **закрываются в Task 7** (PSA на уровне `restricted` + OPA Gatekeeper
  constraints, запрещающие `privileged: true`).

### 3. Использование `kubectl exec` в чужом поде (`exec-in-pod`)

- **Кто**: `minikube-user`.
- **Где**: `pods/exec` в `kube-system/coredns-...`.
- **Результат**: `101 Switching Protocols` — websocket-сессия успешно
  открыта. То есть exec прошёл.
- **Почему подозрительно**: `exec` в чужом namespace, тем более в
  `kube-system`, — стандартный приём для расширения присутствия в
  кластере. coredns содержит конфигурацию DNS-плоскости, доступ к нему
  позволяет атаковать имена служб.
- **Какой контроль провален**: `K8S-01` — RBAC должен разрешать exec
  только в свой namespace (см. **Task 4**: `prop-namespace-developer` не
  даёт прав вне домена). Здесь exec выполнен от cluster-admin, потому
  что в учебной среде он у нас единственный пользователь.

### 4. Создание RoleBinding с правами `cluster-admin` (`cluster-admin-binding`)

- **Кто**: `minikube-user`.
- **Где**: `secure-ops/rolebindings/escalate-binding`.
- **Что**: `roleRef.name = cluster-admin` (`ClusterRole`), `subjects = ServiceAccount monitoring`.
- **Результат**: `201 Created` — биндинг создан.
- **К чему привело**: после этого изменения ServiceAccount `monitoring`
  получил **права cluster-admin внутри namespace secure-ops** через
  RoleBinding. Это эквивалентно полному контролю над пространством
  secure-ops и существенному увеличению атакующих возможностей оттуда
  (создание новых ресурсов, мониторинг событий и т.д.).
- **Какой контроль провален**: `AUTHZ-02` и `K8S-01` из Task 2.
  В нормальной модели RBAC из **Task 4** только группа `prop-platform-admins`
  имеет право выдавать роли `cluster-admin`. Здесь — обычная учётка с
  cluster-admin импликативно может всё, и это и есть проблема.

### 5. Тампер audit-policy (`audit-policy-tamper`)

В extract — три связанных события (GET 404 → CREATE 201 → DELETE 200) на
ConfigMap с именем `audit-policy` в namespace `secure-ops`.

- **Кто**: `minikube-user`.
- **Где**: `secure-ops/configmaps/audit-policy`.
- **Возможные последствия**: имя `audit-policy` — маркер для нашего
  скрипта-фильтра. Атакующий может пытаться создать одноимённый ConfigMap,
  чтобы скрыть аномалии в логах, имитировать «легитимную» работу с политикой
  или попытаться повлиять на скрипты, которые её парсят. В нашей лабе
  ConfigMap-у не дано никаких реальных функций — но в продакшене, где
  audit-policy.yaml лежит на ноде, нужен контроль целостности этого файла
  (например, hash в SIEM с автоматическим алертом на изменение).
- **Дополнительно** в логе была попытка `kubectl delete -f /etc/kubernetes/audit-policy.yaml --as=admin` — она вернула `the path "..." does not exist` и не дошла до API-сервера, поэтому в `audit-extract.json` напрямую не попала, но сам факт `--as=admin` зафиксирован в полном `audit.log`.

## Что можно считать компрометацией кластера

Любое одно из этих событий — серьёзный сигнал; в совокупности это
**сценарий начала компрометации**:

1. **Цепочка escalate-binding → privileged-pod** — атакующий поднял
   привилегии аккаунта, затем получил host-уровневый доступ. После
   privileged-pod возможен прорыв на ноду и кража kubeconfig-ов всех
   пользователей.
2. **`exec` в `kube-system`** — точка перехвата трафика и DNS.
3. **Чтение секретов в `kube-system` под чужим именем** — даже неудачное,
   доказывает попытку разведки.

При наблюдении хотя бы трёх событий **за одну минуту** SIEM/SOC должен
автоматически закрывать инцидент как **подтверждённую компрометацию**
с активацией IR-плейбука (см. контроли `IR-01..05` в Task 2).

## Какие ошибки допускает текущая политика RBAC

Все события в нашем учебном кластере прошли от `minikube-user` со
`system:masters`-членством (фактический cluster-admin). В реальной
PropDev-конфигурации такая модель — заметно слабее, чем модель RBAC,
которую мы реализовали в **Task 4**. Какие именно зазоры RBAC сделали
эту цепочку возможной:

| Ошибка модели RBAC | Что нужно делать | Где закрыто |
| ------------------ | ---------------- | ----------- |
| Единая привилегированная учётка для оператора + разработчика + аудитора | Разделить на `prop-platform-admins`, `prop-security-officers`, `prop-namespace-developer`, ...; см. таблицу ролей в Task 4 | [Task 4](../Task4/roles-table.md) |
| Возможность создать RoleBinding с `roleRef: cluster-admin` любым неприви­лигированным пользователем (если ему когда-либо выдали `rolebindings.create`) | RoleBinding-ы выдавать только из группы `prop-platform-admins`, остальные роли не имеют `create/update/patch` на RBAC ресурсы. В нашей модели разработчик в namespace явно запрещён трогать RBAC | [Task 4 §намespace-developer](../Task4/roles-table.md) |
| ServiceAccount `default` принимает любые токены по-умолчанию | Отключать `automountServiceAccountToken: false` для всех подов, не использующих API. Контроль `K8S-06` из Task 2 | Будет частью Task 7 |
| privileged-pod не блокируется на уровне admission controller | Использовать PodSecurity Admission с уровнем `restricted` + OPA Gatekeeper с запретом `privileged: true` | Task 7 |
| Аудит-лог сам по себе не защищён от удаления (статический файл на ноде) | Реплицировать аудит в SIEM в реальном времени; ввести WORM-режим для архивных копий. Контроль `AUDIT-02` | Не реализовано в лабе, документировано в Task 2 |

## Вывод

- Все пять видов подозрительной активности из ТЗ воспроизведены и
  зафиксированы аудит-логом. Скрипт фильтрации (`analyze-audit.sh`)
  сводит их в `audit-extract.json` и выдаёт сводку по категориям.
- Подтверждено: **без включённого аудита** ни одно из этих событий
  не было бы видно — даже отказы доступа (403, `auth can-i`) проходят
  «тихо». Это и есть ключевой контроль из проверочного листа Task 2:
  без `AUDIT-01..05` невозможна детекция инцидентов.
- Текущая модель RBAC (универсальный cluster-admin) — пример того, как
  делать **нельзя**. Корректную ролевую модель мы выстраиваем в
  **Task 4**, изоляцию трафика — в **Task 5**, защиту от опасных подов —
  в **Task 7**.
- Аудит-лог — это **последняя линия обороны**: даже когда атакующий уже
  внутри, он оставляет следы. Защищать сам лог (целостность, экспорт в
  SIEM, репликация) — отдельный must-have, документированный как
  `AUDIT-02` в Task 2.

## Связанные артефакты

- `audit-policy.yaml` — действующая audit policy.
- `setup-audit.sh` — настройка Minikube apiserver под аудит.
- `simulate-incident.sh` — генератор подозрительной активности.
- `analyze-audit.sh` — скрипт фильтрации (Bash + jq).
- `audit.log` — полный аудит-лог (выгружен из ноды Minikube).
- `audit-extract.json` — выжимка отфильтрованных событий с категориями.
